# Guará CLI

## Overview

Guará provides a command-line interface for managing and executing transaction workflows.

The CLI is designed primarily for **operational execution and recovery**, providing a lightweight interface for replaying transaction executions recorded in execution history.

The current CLI exposes the following command:

```text
guara replay
```

The general structure is:

```text
guara
└── replay
```

## Installation

The CLI is installed together with Guará.

After installing the package, verify the installation with:

```bash
guara --version
```

To display the available commands:

```bash
guara --help
```

## `replay`

The `replay` command re-executes transaction executions recorded in a transaction log.

```bash
guara replay
```

It can be used to:

* replay a complete execution;
* target a specific transaction;
* target a specific execution using its identifier or hash;
* resume an execution from a selected point;
* inject the driver required by the transactions.

The command is particularly useful for **failure recovery, operational debugging, and reproducing previous executions**.


## Replay Help

Run:

```bash
guara replay --help
```

Output:

```text
usage: guara replay [-h] [-f FILE] [-i ID] [-r] [-d DRIVER]

options:
  -h, --help            show this help message and exit
  -f FILE, --file FILE  Path to the JSON transaction log file to replay.
  -i ID, --id ID        Specific transaction identifier or execution hash to target.
  -r, --resume          Resume the replay execution from a specific transaction or execution ID.
  -d DRIVER, --driver DRIVER
                        Python path to the driver class or factory. Example: drivers:create_driver
```


## Replay Options

## `-f`, `--file`

Specifies the transaction log file used as the source for the replay.

```bash
PYTHONPATH=$(pwd) guara replay --file execution.json
```

Short form:

```bash
PYTHONPATH=$(pwd) guara replay -f execution.json
```

The file contains the persisted execution history generated by Guará.

### Example

```bash
PYTHONPATH=$(pwd) guara replay -f logs/order_execution.json
```


## `-i`, `--id`

Specifies a transaction identifier or execution hash to target.

```bash
PYTHONPATH=$(pwd) guara replay -f execution.json --id <ID>
```

Short form:

```bash
PYTHONPATH=$(pwd) guara replay -f execution.json -i <ID>
```

This allows a particular execution within the log to be selected instead of replaying the entire recorded workflow.

An identifier may represent:

* a transaction identifier;
* an execution identifier;
* an execution hash.

The exact identifier should correspond to the identifiers recorded in the execution history.


## `-r`, `--resume`

Resumes execution from a specific transaction or execution ID.

```bash
PYTHONPATH=$(pwd) guara replay -f execution.json -i <ID> --resume
```

Short form:

```bash
PYTHONPATH=$(pwd) guara replay -f execution.json -i <ID> -r
```

Without `--resume`, the selected transaction/execution is replayed according to the normal replay behavior.

With `--resume`, the selected point is treated as the point from which the workflow should continue.

### Example

Suppose the original workflow was:

```text
CreateCustomer
    ↓
CreateOrder
    ↓
ProcessPayment
    ↓
SendNotification
```

If execution failed during `ProcessPayment`, a resume operation can be used to continue the recorded workflow from the relevant execution point rather than manually reconstructing the entire workflow.

```bash
PYTHONPATH=$(pwd) guara replay \
    --file execution.json \
    --id <execution-id> \
    --resume
```


## `-d`, `--driver`

Provides the Python path to the driver class or factory required by the application.

```bash
PYTHONPATH=$(pwd) guara replay \
    --file execution.json \
    --driver drivers:create_driver
```

The driver is supplied at replay time rather than persisted in the execution log.

This is important because a driver represents a runtime infrastructure dependency.

The execution history can therefore remain independent from the concrete driver instance used during replay.


## Driver Path Format

The driver argument uses a Python module path followed by `:` and the attribute containing the driver class or factory.

```text
module.path:attribute
```

For example:

```text
drivers:create_driver
```

or:

```text
myproject.infrastructure.driver:Driver
```

The attribute may represent the driver class or a factory used to create the driver.

### Example

```bash
PYTHONPATH=$(pwd) guara replay \
    --file execution.json \
    --driver drivers:create_driver
```

Conceptually, the CLI resolves:

```text
drivers
   └── create_driver
```

and provides the resulting driver to the Guará `Application` used for replay.

```python
from selenium import webdriver


def create_driver():
    driver = webdriver.Chrome()
    driver.get("https://myapplication.com")
```


## Common Usage Patterns

## Replay a Log

```bash
PYTHONPATH=$(pwd) guara replay -f execution.json
```

Use this when the complete recorded execution should be replayed.


## Replay a Specific Execution

```bash
PYTHONPATH=$(pwd) guara replay \
    -f execution.json \
    -i <execution-id>
```

Use this when the log contains multiple transaction executions and only one should be targeted.


## Resume an Execution

```bash
PYTHONPATH=$(pwd) guara replay \
    -f execution.json \
    -i <execution-id> \
    --resume
```

Use this to continue a workflow from a selected transaction or execution point.


## Replay with a Driver

```bash
PYTHONPATH=$(pwd) guara replay \
    -f execution.json \
    -d drivers:create_driver
```

Use this when the replayed transactions require access to external infrastructure through a driver.


## Replay a Specific Execution with a Driver

```bash
PYTHONPATH=$(pwd) guara replay \
    -f execution.json \
    -i <execution-id> \
    -d drivers:create_driver
```

This is the typical pattern for replaying an execution that depends on runtime infrastructure.


## Resume with a Driver

```bash
PYTHONPATH=$(pwd) guara replay \
    -f execution.json \
    -i <execution-id> \
    --resume \
    --driver drivers:create_driver
```

This combines execution recovery with runtime dependency injection.


## CLI and Application Architecture

The CLI does not replace the Guará `Application`.

Instead, it acts as an **operational entry point** for the application replay functionality.

The architecture can be represented as:

```text
Command Line
     │
     │ guara replay
     ↓
Replay CLI
     │
     ├── execution log
     ├── transaction ID
     ├── resume
     └── driver
            │
            ↓
      Application
            │
            ↓
      Transaction
            │
            ↓
       Driver / Infrastructure
```

This boundary is intentional.

The CLI is responsible for:

* parsing command-line arguments;
* resolving the driver;
* selecting the replay target;
* invoking replay.

The `Application` remains responsible for the actual transaction orchestration and replay semantics.


## Operational Recovery

The CLI is particularly useful when combined with Guará's execution history.

A production workflow can follow this lifecycle:

```text
Application execution
        ↓
Execution History
        ↓
       Dump
        ↓
 JSON log
        ↓
   guara replay
        ↓
Select execution
        ↓
Optional driver injection
        ↓
Replay / Resume
```

This provides a practical recovery mechanism without requiring application code to implement a separate replay command for every workflow.

---

## Design Principles

The CLI follows several important architectural principles.

## Execution history is portable

The persisted log contains execution information, while runtime infrastructure such as drivers is supplied when replaying.

## Replay is application-level

The CLI does not implement transaction behavior itself. It delegates replay to Guará's application orchestration layer.

## Driver dependencies remain external

Drivers are runtime dependencies and are injected into the replayed `Application` rather than serialized as part of the execution history.

## Recovery is explicit

Selecting an execution and deciding whether to resume it are explicit CLI operations:

```text
--id
--resume
```

This avoids implicit recovery behavior.

## End-to-End Example

Assume an execution was previously persisted as:

```text
logs/order_execution.json
```

The workflow requires a driver created by:

```text
drivers:create_driver
```

A complete replay can be started with:

```bash
PYTHONPATH=$(pwd) guara replay \
    --file logs/order_execution.json \
    --driver drivers:create_driver
```

To target a specific execution:

```bash
PYTHONPATH=$(pwd) guara replay \
    --file logs/order_execution.json \
    --id 8f4c2a \
    --driver drivers:create_driver
```

To resume from that execution:

```bash
PYTHONPATH=$(pwd) guara replay \
    --file logs/order_execution.json \
    --id 8f4c2a \
    --resume \
    --driver drivers:create_driver
```

The resulting operational model is:

```text
                  execution
                      │
                      ▼
              execution history
                      │
                      ▼
              JSON transaction log
                      │
                      ▼
              ┌───────────────┐
              │ guara replay  │
              └───────┬───────┘
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
        --file      --id      --resume
                                  │
                                  ▼
                              continue
                      │
                      ▼
                   --driver
                      │
                      ▼
                Application
                      │
                      ▼
                 Transactions
```

The CLI therefore provides a simple operational surface over Guará's transaction execution and recovery capabilities while keeping orchestration semantics inside the framework itself.
